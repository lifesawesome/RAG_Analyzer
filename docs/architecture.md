# Solution Architecture and Execution Walkthrough

Documented: 2026-11-12. This describes the code and saved verification results of the **implemented demo**, not a fresh Azure inventory or the full production design in the original plan.

## 1. What the Solution Does

A compliance analyst asks a question in a local browser application. A saved Microsoft Foundry prompt agent uses GPT-4.1 to request a search. The local Python backend executes that search against an Azure Databricks hybrid index, returns permitted evidence to Foundry, validates the answer's citation IDs, and presents the answer alongside the source passages and original PDF pages.

The recorded live deployment contained 40 PDFs: 20 public BIS/Basel Committee reports and 20 explicitly fictional bank-policy PDFs, with 6,560 indexed chunks. In this public guide, `rag_demo.rag.policy_chunks_index_dated` is an example index name; configure your own catalog and index locally.

**Ownership in one sentence:** Databricks processes, embeds and retrieves documents; Foundry selects the tool and generates the answer; the local backend controls tool execution, demo access predicates, citation mapping and the browser response.

There are three separate workflows:

| Workflow | When it runs | Result |
| --- | --- | --- |
| Knowledge preparation | An operator explicitly runs the corpus, upload, notebook and finalization scripts | PDFs become parsed Delta records, chunks, embeddings and a searchable index |
| Online research | A user submits a question | Foundry receives filtered Databricks evidence and produces a cited answer |
| Source inspection | A user opens a source or changes a preview page | The backend renders a local copy of the PDF; this makes no model call |

See the [application and component diagrams](../.github/modernize/assessment/engines/facts/architecture-diagram.md) for the two-layer visual architecture. The original [project plan](../plan-azureDatabricksFoundryRag.prompt.md) describes the broader intended solution; features in that plan are not automatically implemented.

The Databricks-managed group contains service-owned infrastructure. It is not a third application tier to administer manually. No standalone VM, AKS cluster, APIM instance or public application host was added for this demo.

## 4. Knowledge Preparation: Every Step

The owning source files are [the corpus utility](../app/corpus.py), [the live runner](../scripts/live_databricks.py), [the notebook](../notebooks/01_databricks_rag.ipynb) and [the finalizer](../scripts/finalize_live_index.py).

1. **Generate fictional policies.** The corpus utility uses ReportLab to create 20 PDFs from ten policy topics. Versions, effective dates and restricted/future fixtures support demonstration scenarios. These are not actual bank policies or regulations.
2. **Download public reports when explicitly requested.** The downloader follows the configured BIS URLs. If a URL resolves to a publication HTML page, it parses links and restricts candidate PDF downloads to approved BIS HTTPS hosts.
3. **Validate downloaded content.** The utility checks the PDF signature, limits a download to 100 MB, opens it with pypdf and derives a title. Unavailable reports are reported rather than silently counted as valid PDFs.
4. **Build the manifest.** Each entry records its document ID, local path, SHA-256, public reference where available, version and demo governance labels. Hashes verify bytes and contribute to chunk identity; they are not a complete cross-document deduplication policy.
5. **Connect to the approved workspace.** The live runner uses the official Databricks SDK with `azure-cli` authentication and the target tenant. Its explicit host/tenant arguments must match the locally configured workspace/tenant.
6. **Guard the destination.** The runner uses the existing catalog with managed storage. It creates a dedicated schema and Volume with an ownership marker derived from the explicit subscription ID; if matching objects already exist without that marker, it refuses to overwrite their contents as this demo. The finalizer requires the same marker and an explicitly selected SQL warehouse.
7. **Upload the source material.** The runner verifies unique document IDs, safe local paths and matching SHA-256 values, then uploads PDFs and the manifest through the Databricks Files API. Existing source paths in the marked demo Volume may be overwritten during an intentional rerun.
8. **Prepare an execution copy of the notebook.** The adapter changes the default catalog to the approved existing catalog, uses `USE CATALOG` rather than attempting an unconfigured new catalog, pins `typing-extensions==4.16.0`, inserts a Python restart after installation, and adds a receipt-exit cell. It stages a content-hashed remote notebook path without modifying the local source notebook.
9. **Start bounded serverless processing.** The task uses standard performance mode, no explicitly configured cluster, `max_retries=0`, and a configured task timeout of 1,800 seconds in the recorded run. The serverless runtime is separate from local Python 3.13.
10. **Read and validate the uploaded manifest.** The notebook checks document IDs, paths, PDF extensions, file sizes, source hashes and required tenant/group metadata. Spark reads PDF binary files and joins them to metadata by filename; the joined file count must match the manifest.
11. **Write Bronze.** File information, binary content, document metadata and ingestion timestamp are written into `bronze_docs`. This notebook uses overwrite for its dedicated Bronze table, not a deployed Auto Loader streaming ingestion pipeline.
12. **Extract Silver pages.** The live parser is pypdf in a Spark UDF. It reads PDF bytes, extracts text per page and preserves one-based page numbers. A parse exception or document above the 500-page guard produces no pages. Whitespace-only page text is excluded.
13. **Record unusable documents.** A document with no usable extracted pages is written to `quarantine_docs` with a generic parse status. Silver rows are written to `silver_docs` with text-extracted/parser labels. Partial missing pages are not a complete per-page quality/quarantine workflow.
14. **Split page text.** `RecursiveCharacterTextSplitter` uses `chunk_size=600` and `chunk_overlap=80`. These are **characters, not tokens**. Splitting is page-based; it does not implement a legal-section hierarchy, parent-section expansion or guaranteed table reconstruction.
15. **Assign chunk identity.** SHA-256 combines document ID, source hash, page number, chunk position, parser label, splitter settings and chunk text. Empty text is excluded, and chunk IDs are deduplicated.
16. **Write Gold and enable CDF.** The notebook creates the original Gold Delta table or MERGEs on `chunk_id`, updates matching rows, inserts new rows and deletes target rows missing from the source snapshot. It enables `delta.enableChangeDataFeed=true` and checks primary-key uniqueness. This reconciliation affects only the dedicated demo table; it is not incremental source ACL ingestion.
17. **Create the initial managed index.** The notebook reuses or creates a standard endpoint and triggered Delta Sync index. Databricks generates ingestion embeddings with `databricks-qwen3-embedding-0-6b` and maintains the index from the chosen source table when a synchronization is triggered.
18. **Finalize the deployed date schema.** The first live query rejected a range filter because the initial date column was text. The finalizer creates `policy_chunks_dated` with `CAST(effective_date AS DATE)` and CDF, then creates the separate `policy_chunks_index_dated`. The original index is preserved. The SQL warehouse started by the finalizer is stopped in its cleanup path.
19. **Verify the completed data path independently.** The final notebook run timed out, so it remains recorded as `TIMEDOUT`. Independent index reads established readiness and 6,560 rows. Real filtered query results and a Foundry answer, rather than a rewritten notebook status, establish the verified live demo.

The notebook includes an optional `ai_parse_document` branch that handles structured elements from VARIANT output and page references. That branch was not the verified live parsing path. OCR, rigorous layout/table fidelity and structured legal-section chunking need separate validation.

## 6. Online Research: Every Request Step

The central implementation is [the research route](../app/main.py), [the cloud adapters](../app/cloud.py) and [the contracts](../app/contracts.py).

1. **The browser submits the question.** The UI sends only the query, as-of date and result limit to the same-origin API. It does not send Azure credentials or a claimed role.
2. **The local HTTP boundary runs.** The backend accepts loopback clients, enforces allowed Host values and rejects POST requests with a supplied mismatched Origin. These checks are a presenter-only boundary, not a substitute for production authentication/CSRF controls.
3. **Pydantic validates the input.** Query length is 3-2,000 characters, `top_k` is 1-8 and defaults to 6, and the date must parse as a date. Unknown request properties are forbidden; a caller cannot add their own tenant or filter object.
4. **The backend creates request metadata.** It starts a timer and UUID request ID. It uses its preconstructed `AccessContext`, including configured tenant/group values and allowed classifications.
5. **Configuration is checked.** Live mode requires HTTPS Databricks/Foundry endpoint shapes. This configuration check is not itself proof that remote services are reachable.
6. **The backend authenticates to Foundry.** `AzureCliCredential` is pinned to the configured Entra tenant, and the Azure AI Projects client connects to the configured project and saved agent.
7. **A new conversation is created.** The application does not reuse an old browser conversation or accept a conversation ID from the caller. Every submitted question is a separate conversation.
8. **The first Responses API request runs.** The question is sent to the saved agent, with an output-token ceiling of 1,200. GPT-4.1 reasons about the question and is instructed to retrieve before making corpus-dependent claims.
9. **The agent returns a function-call request.** Its allowed function is `search_compliance_documents`; its only model-controlled parameter is `query`. The agent can reformulate that query, but cannot select an index, tenant, group, classification or as-of date.
10. **The backend validates the requested tool.** It verifies the tool name, exact argument keys, string type and 1-2,000-character search-query bound. It permits one call in a response, bounds the loop to four iterations and rejects additional retrieval after nonempty evidence has already been collected. Empty retrievals can still lead to further calls within the loop budget; this is not an unlimited research agent.
11. **The backend builds the search predicates.** Tenant, allowed ACL groups, allowed classifications and `effective_date <= as_of` come from server settings/request date, not the model's arguments.
12. **The backend authenticates to Databricks and queries.** It obtains a tenant-scoped Databricks token, sends `query_type=HYBRID`, selects citation/governance/text columns and passes `filters_json` to the configured standard index. The REST timeout is 60 seconds.
13. **Databricks retrieves evidence.** The managed search service computes the query embedding using the configured Databricks model and combines semantic and keyword retrieval. Indexed metadata predicates restrict returned rows. The application does not implement a separate reranker, query decomposition, parent expansion or a broad candidate/rerank stage.
14. **The backend reconstructs and rechecks results.** It maps the returned column manifest to each row and checks tenant, group, classification and effective date again before returning evidence to the agent. This second check protects the current fixture contract; it does not query an independent up-to-date entitlement registry.
15. **Evidence IDs are assigned for this response.** `E1`, `E2` and so forth correspond to the returned evidence list. They are response-local labels, not globally stable chunk IDs. Stable `chunk_id` and `doc_id` remain in the full API evidence.
16. **Authorized grounding text goes back to Foundry.** The backend submits a `function_call_output` containing evidence ID, title, page, version and text. Tokens, credentials, the access context and raw PDF binaries are not included. The full source metadata stays in the backend's evidence objects for the UI.
17. **The agent generates its answer.** It is instructed to use the evidence only, distinguish fictional policies from public regulations, ignore document-embedded instructions, state gaps and return a JSON object with answer text and citation IDs.
18. **The backend validates the final structure.** It requires exactly `answer` and `citations`, a nonempty answer and citation IDs from the evidence whitelist. When evidence exists, at least one valid citation is required. This validates citation identity, **not semantic entailment of every claim**. If no evidence was collected, the backend supplies an explicit cannot-answer response with no citations.
19. **The conversation is cleaned up.** In a `finally` block the application attempts deletion. If it fails, a cleanup warning is added to the trace; the app does not claim deletion succeeded. It does not provide production retention/audit guarantees or a persistent chat history.
20. **The browser receives the receipt.** The API returns answer, citations, evidence, query/as-of date, mode, request ID, corpus count, elapsed time, filter object and trace. The UI renders strings using `textContent` and can export the receipt. It refreshes process status and shows `LIVE VERIFIED` after the required service stages have succeeded in that process.

### Request and Tool Contract

Illustrative valid HTTP body for `POST /api/ask`:

```json
{
  "query": "What approvals apply to elevated-risk commercial lending?",
  "as_of": "2026-11-11",
  "top_k": 6
}
```

Actual filter structure used by the verified standard-index query:

```json
{
  "tenant_id": "us-commercial",
  "acl_group": ["compliance-analysts"],
  "classification": ["public", "synthetic", "confidential"],
  "effective_date <=": "2026-11-11"
}
```

The model's function input is only a query. An illustrative compact grounding output is:

```json
[
  {
    "evidence_id": "E1",
    "title": "Commercial lending policy",
    "page": 1,
    "version": "2.0",
    "text": "Synthetic demo policy excerpt requiring independent credit review."
  }
]
```

An illustrative accepted answer shape is:

```json
{
  "answer": "The synthetic demo policy requires independent credit review. This is not a statement of actual regulatory requirements.",
  "citations": ["E1"]
}
```

The active integration is **application-executed function calling**, not a remote MCP or OpenAPI tool. Foundry returns a call request over its API; the backend performs retrieval and sends the result back in the same conversation. Merely viewing the saved agent in a portal does not replace this application execution loop.

## 7. Source PDF Viewing: Every Step

1. The user selects Open source on an evidence passage, or Open PDF in the corpus view.
2. The browser uses its `doc_id` and page number to call the local preview route.
3. The backend looks up that ID in the local manifest. Arbitrary URLs and file paths are not accepted as source identifiers.
4. It checks the fixed presenter's tenant, group, classification and the document date against **today's server date**. Source access does not reuse the research request's as-of date, and therefore is not a complete historical-document authorization system.
5. A path helper verifies that the resolved file remains inside the configured local data directory.
6. Under a render lock, PDFium opens the PDF, checks one-based page bounds and renders the page at scale 1.5 to PNG.
7. The API returns image bytes and `X-Page-Count`; the browser creates a temporary object URL, displays the page and enables valid previous/next actions.
8. The original PDF link uses the separately guarded local PDF route. Rendering and opening sources do not invoke Foundry or fetch a document from Azure storage on demand.

Keeping local PDFs is therefore a real runtime dependency even in live mode. If an operator removes or changes those local copies without updating the cloud corpus consistently, research can still retrieve cloud chunks while the preview is missing or no longer matches them.

## 8. API Surface

| Method and route | Input/output | Current behavior |
| --- | --- | --- |
| `GET /` and static files | HTML/CSS/JavaScript | Served by the same local FastAPI process |
| `GET /api/status` | Mode, local counts, scope and last-success flags | Reads local configuration/process state; does not run remote health probes |
| `GET /api/documents` | Permitted manifest metadata | Uses today's date; excludes local file paths and hashes from the list response |
| `GET /api/documents/{doc_id}` | PDF bytes | Manifest lookup, demo permission check and safe local path |
| `GET /api/documents/{doc_id}/preview/{page_number}` | PNG bytes and page-count header | Same permission boundary plus PDF page bounds |
| `POST /api/ask` | Validated question; answer/evidence/trace receipt | Mode-specific retrieval and optional Foundry reasoning |

Unknown, restricted or out-of-range source requests return 404. Request-schema errors return 422. Cross-origin POST or non-loopback client rejection returns 403. Trusted-host rejection is handled by middleware. Research adapter/service/answer-validation failures return 503; no local substitute answer is silently returned.

## 9. Authorization and Governance: What Is Enforced

The server creates a fixed context with `DEMO_TENANT_ID` and `DEMO_ACL_GROUPS`; allowed classifications are the code-defined tuple `public`, `synthetic`, `confidential`. The Azure tenant GUID is an authentication-directory ID; `us-commercial` is a demo document boundary. They are different concepts.

Both request filtering and candidate rechecking require the matching demo tenant, an allowed nonempty group, an allowed classification and a date no later than the selected as-of date. The browser cannot supply extra identity/filter fields, and a caller identity header is not trusted. Unity Catalog grants control access to the index, but do not by themselves establish document-level filtering for each analyst.

Important limits:

- All browser callers on this presenter machine share one configured access context. No Entra browser login or end-user delegation is implemented.
- Public report governance metadata is deliberately artificial. `effective_date=2026-01-01` is not the publication's real legal effective date, and a demo group is not a source-system ACL.
- Filtering uses only a lower-bound effective date. There is no `effective_to`, supersession rule, latest-version selection, transaction-time policy history or historical entitlement snapshot. Versions 1.0 and 2.0 may both be returned.
- There is no independent entitlement registry or immediate revocation check against SharePoint/Entra. Stale indexed metadata remains a production risk.
- Citation-whitelist validation does not prove that the model's statement follows from the cited passage. Groundedness/entailment evaluation and human review remain necessary.
- Prompt instructions tell the model to treat PDFs as untrusted evidence. This reduces risk but is not a proof of immunity to indirect prompt injection.
- Do not expose the loopback API through a tunnel or change the bind address without replacing the presenter boundary with real authentication/authorization.

## 10. Modes and Failure Handling

| `RAG_MODE` | Retrieval | Answer generation | Cloud use |
| --- | --- | --- | --- |
| `offline` | Local SQLite FTS5 BM25 over cached pypdf text | Fixed extractive-retrieval message, not an LLM answer | None for a question |
| `databricks` | Actual configured Databricks hybrid index | Fixed extractive-retrieval message | Databricks query and embedding use |
| `foundry` | Actual configured Databricks hybrid index via the agent's function request | Saved Foundry prompt agent using GPT-4.1 | Foundry plus Databricks |

Offline parsing/cache behavior is in [app/local_search.py](../app/local_search.py). Its cache fingerprint includes manifest content, actual PDF-byte hashes and splitter settings; unchanged files avoid reparsing. It is not a live-mode retrieval cache.

In live modes, malformed service output, authentication failure, an invalid citation or a Databricks query error causes request failure rather than a switch to local search. No evidence produces explicit abstention. The UI shows the error and re-enables submission; it does not auto-retry a costly question indefinitely. Query execution is bounded by the tool-loop/output limits and service timeouts, not a production end-to-end SLA.

## 11. Updates, Synchronization and Reruns

**Triggered sync is not continuous sync.** Source-table changes are not assumed queryable until an explicit sync finishes. A CREATE response or an online endpoint alone does not establish that the intended rows are indexed.

The original notebook can reconcile its original Gold table and trigger the original index. However, the active DATE-typed table was created by `CREATE TABLE IF NOT EXISTS ... AS SELECT`. It is a **snapshot**, not a live view. Re-running the finalizer does not refresh an existing snapshot and does not automatically sync an existing versioned index.

For a future corpus change, an operator must design and validate all of the following before publishing the update: source/manifest reconciliation, original Gold refresh, DATE-typed projection refresh, appropriate delete handling, explicit active-index synchronization, index readiness and regression queries. Do not assume that rerunning the upload script or notebook alone updates the currently configured live index. Production would require an owned refresh pipeline and security-revocation strategy.

The provided runners are scoped to this demo. Notebook overwrite/MERGE behavior must not be pointed at shared production tables. The scripts do not automatically remove old indexes, old subscriptions or resource groups. Old-project deletion is still a separately confirmed action in the saved migration record.

## 12. Traces, Evidence and Verification

The application trace is assembled by the backend, not a deployed distributed tracing platform. It records service stages, response IDs, timing and server predicates. Foundry's own internal traces are not assumed to show Databricks filter details. The verification utility uses a placeholder zero for its retrieval-stage milliseconds; use the web API's measured retrieval duration for that metric, not the utility placeholder.

| Evidence | What it establishes |
| --- | --- |
| Local `live-rag-receipt.json` | A real hybrid query, permitted evidence, denied-cohort/tenant/date cases and a real Foundry function-tool answer |
| Local `live-browser-receipt.json` | Actual web API result from a live browser-validation run |
| Local `live-downloaded-receipt.json` | The browser's explicit JSON export path |
| Local migration records | Recorded deployment, active index and any pending cleanup |
| Local `live-databricks-run.json` | Actual submitted run outcome, including timeout; not evidence that every notebook cell completed |
| Local `dated-index.json` | Creation of the typed projection/index and owned SQL warehouse shutdown |
| Local live desktop/trace screenshots | Recorded UI state with evidence and service stages |

These are generated under the ignored local artifacts directory and are not distributed with the repository. Older local receipts may use environment-specific filenames.

Recorded checks include 30 passing local tests, live unknown-group/cross-tenant/historical-date denials, and desktop/mobile research, source rendering, trace, receipt-download and layout checks. These are demo correctness checks, not a production capacity test, compliance certification, measured Recall@k study or a guarantee of zero hallucinations.

## 13. Operator Runbook

Run the local server from the workspace root with a working Azure CLI sign-in to the new tenant:

```powershell
az account show --query "{subscription:id,tenant:tenantId}" -o json
.\scripts\Start-Demo.ps1 -Mode foundry -Port 8766
```

The launcher installs the repository requirements, chooses another port if the requested one is occupied, and prints its URL. Keep that process running. Existing environment variables take precedence when dotenv loads settings, and the launcher explicitly selects its mode. Restart after changing configuration; do not assume the existing process reloads its settings.

These commands make real cloud calls and incur usage charges:

```powershell
.\.venv\Scripts\python.exe scripts/verify_live_rag.py --execute
.\.venv\Scripts\python.exe scripts/browser_smoke.py --url http://127.0.0.1:8766 --allow-live
```

For local checks without model/search requests:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\scripts\Start-Demo.ps1 -Mode offline
```

Normal question answering does not need the PDF ingestion notebook, Spark compute or SQL warehouse to be restarted. It does need a ready search endpoint/index, embedding access, Foundry model capacity, valid CLI authentication and local PDFs if source previews are required.
